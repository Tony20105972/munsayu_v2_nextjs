# MUNSAYU V2 — 목표 시스템 설계도 (Blueprint)

> 이 문서는 **완성될 시스템의 모양**을 정합니다. 두 종류의 내용이 있습니다.
>
> - **[확정]** 지금 정할 수 있는 원칙. Claude는 이것을 바꾸지 않습니다. 바꿔야 할 이유가 생기면 ADR을 제안하고 사람 승인을 받습니다.
> - **[Claude 작성]** 레거시 조사 결과가 있어야 채울 수 있는 빈칸. 표시된 Phase에서 Claude가 증거를 바탕으로 채웁니다. 각 칸에는 근거 증거 ID(`EV-xxxx`)나 기능 ID를 함께 적습니다.
>
> 세부 산출물(라우트 맵, 스키마, OpenAPI)은 `docs/contracts/`에 둡니다. 이 문서는 그것들을 잇는 큰 그림만 담고, 내용을 중복해서 적지 않습니다.

---

## 1. 시스템 개요 [확정]

- **하나의 Next.js 앱**이 공개 사이트, 신청 처리, 관리자 화면을 모두 맡습니다 (모듈형 모놀리스).
- 런타임에 레거시 PHP 서버를 호출하지 않습니다.
- 외부 의존은 DB, 파일 저장소, 알림 공급사, 분석 스크립트로 한정합니다.

```
브라우저
  │
  ▼
Next.js 앱
  ├─ 공개 영역      app/(public)/      ── Server Components
  ├─ 관리자 영역    app/admin/         ── 로그인 필수, RBAC
  ├─ API           app/api/           ── 외부 호출용 Route Handlers
  └─ 서버 계층      src/server/
       ├─ services/   비즈니스 규칙 (신청·예약·콘텐츠)
       ├─ auth/       세션·권한
       ├─ adapters/   알림·저장소 등 외부 연동
       └─ db.ts       Prisma (서버 전용)
  │
  ▼
PostgreSQL (D2에 따라 변경 가능) · Object Storage · 알림 공급사
```

## 2. 계층 책임 [확정]

| 계층 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 페이지·컴포넌트 | 화면 표시, 사용자 입력 받기 | DB 직접 접근, 권한 판단 |
| Server Action / Route Handler | 입력 검증(Zod) → 권한 확인 → 서비스 호출 → 응답 | 비즈니스 규칙 구현 |
| 서비스 | 비즈니스 규칙, 트랜잭션, 상태 전환 | HTTP·쿠키 처리, 화면 문구 |
| 어댑터 | 외부 시스템 호출 | 비즈니스 판단 |
| DB | 저장, 무결성 제약 | — |

요청 흐름은 항상 이 순서입니다:
`입력 → Zod 검증 → 인증·권한 → 서비스(트랜잭션) → 어댑터(알림 등) → 응답`

## 4. 화면 구성 [Claude 작성 — Phase 1 → 2]

### 4.1 공개 페이지 트리
Phase 1의 `legacy-route-map.json`을 근거로 작성합니다. 레거시 URL과 신규 경로를 나란히 적습니다.

```
`/`, `/sub/about`, `/sub/Location`, `/sub/Facility`, `/sub/abouttch1~3`, `/sub/schedule.n`, `/sub/schedule.g`, `/sub/Presentation`, `/sub/Check`은 유지한다. `/bbs/*` 공개 경로는 `/notice`, `/login`, `/register`, `/account/recovery`로 308한다. `/uAdmin/**`와 `/adm/**`는 신규 `/admin`으로 연결하지 않고 410한다. 상세는 `docs/contracts/route-compatibility-map.json`.
```

### 4.2 공통 레이아웃
헤더·푸터·메뉴 구성과 페이지별로 바뀌는 영역.

- `OBSERVED` — 헤더에는 학원안내·강사진안내·시간표·설명회·예약확인/신청 메뉴와 공개 로그인·회원가입 링크가 있다. 푸터에는 강좌/설명회/외부 문해력 진단 신청 링크가 있다. `EV-0003`, `EV-0007`
- `OBSERVED` — 그누보드형 공개 인증 경로(`/bbs/login.php`, `/bbs/register.php`)와 공지 목록/상세 URL 형식이 있다. `EV-0007`

### 4.3 관리자 화면
공개 화면에서 확인할 수 없으므로 대부분 운영자 답변(`PHASE.md` 질문표)과 D5 결정을 근거로 작성합니다.

#### 관리자 기본 범위 [확정]

- **이관 확정:** `AD-001` 관리자 로그인·로그아웃·로그인 유지, `AD-003`~`AD-005` 설명회 관리·상태 변경·예약자/참석 인원 집계, `AD-006` 강사 관리, `AD-007` 시간표 관리, `AD-008` 강좌 수강 신청 목록. 강사·시간표 관리는 레거시에 있으므로 콘텐츠 관리 대상으로 확정합니다.
- **이관 확정:** `AD-002` 공개 회원가입·로그인 및 회원관리. `AD-012`은 자체 접속자 집계 대신 분석 도구 연동 자리(환경 변수 분석 ID)만 제공한다.
- **화면 확인 후 확정:** `AD-009` 입학진단관리, `AD-010` 문자신청내역, `AD-011` 강사지원관리.
- **신규 필수:** `AD-013` 신청자 개인정보 조회·다운로드 기록 및 보존 기간 경과 후 파기.
- 공지·팝업 등 그 밖의 콘텐츠 수정 기능은 운영자 확인 후 확정합니다.
- 신청자 목록 CSV 다운로드와 개인정보 조회는 권한 있는 역할만 수행할 수 있고, 모두 기록을 남깁니다.

## 5. 신청·예약 흐름 [Claude 작성 — Phase 2]

신청 종류마다 아래 네 가지를 적습니다.

1. **사용자 흐름:** 화면 진입 → 입력 → 제출 → 완료 화면 (레거시 관찰 근거)
2. **상태 전환:** 상태 이름과 전환 조건 (다이어그램)
3. **규칙:** 정원, 마감, 중복 신청, 취소 (각각 OBSERVED / INFERRED / UNKNOWN 표시)
4. **알림:** 누구에게, 언제, 어떤 채널로

### 신청 종류 [확정]

- 설명회 신청 — 레거시 신청 폼은 비교 대상에서 제외하고 신규 설계한다. 필드·동의·보유기간 기본안은 강좌 예약 모달(`EV-0006`)을 따른다. 정원·참석 인원 상한·마감·중복·필수 항목은 `D9`에서 확정한다. 공개 예약 조회/취소 화면은 `EV-0008`에 관찰됐으나 신규 흐름 포함 여부는 `UNKNOWN`.
- 강좌 수강 신청 — `EV-ADM-05`에서 강좌별 신청현황이 관찰됐고, 공개 대치 시간표의 예약 모달에서 학생명·보호자 연락처·학교·과정·학년·필수 동의·파기 문구를 관찰했다. `EV-0006`
- 예약 1건에 여러 명이 참석할 가능성은 `INFERRED`이며, 근거는 `EV-ADM-03`의 예약 건수와 참석 인원 분리 집계입니다.

### 고정 규칙 [확정]
- 마감 상태 확인과 저장은 **하나의 트랜잭션**입니다. 설명회와 강좌 모두 정원 숫자로 신청을 막지 않으며, 의도적인 재신청은 허용합니다. 같은 idempotency key 재전송만 중복 저장을 막습니다.
- 모든 신청은 idempotency key로 중복 제출을 막습니다.
- 알림 발송 실패가 신청 저장을 취소시키지 않습니다. 저장 후 발송하고, 실패하면 재시도 대상으로 기록합니다.

## 6. 데이터 [확정 원칙 + Claude 작성]

### 원칙 [확정]
- 스키마의 원본은 `prisma/schema.prisma` 하나입니다.
- 모든 테이블에 `createdAt`, `updatedAt`이 있습니다.
- 신청 기록은 물리 삭제하지 않고 상태로 관리합니다 (보존 기간이 지나면 별도 절차로 파기).
- 개인정보 컬럼은 스키마 주석에 `/// PII`로 표시합니다.
- seed 데이터는 가짜 값만 씁니다.

### 엔터티 개요 [Claude 작성 — Phase 2]
| 엔터티 | 설명 | PII 포함 | 보존 기간 | 관련 기능 ID |
|---|---|---|---|---|
| User/AuthSession | 회원·관리자·세션 | 예 | 탈퇴/보안 정책 | FM-003, AD-001/002 |
| CourseApplication/EventReservation | 신청·예약 | 예 | `PrivacyRetentionSetting` 기준 | FM-001/002, AD-013 |
| Course/Event/EventStatusOption | 공개 콘텐츠·수동 상태 | 아니오 | 해당 없음 | PG-008~010, AD-003~008 |
| Instructor/TeamMembership | 강사와 복수 팀 | 약력은 공개 콘텐츠 | 해당 없음 | AD-006 |
| AuditLog | 개인정보 조회·CSV·파기 기록 | 행위자 식별자 | 보안 정책 | AD-013 |

### 기존 데이터 [Claude 작성 — D1 결정 후]
D1 확정: 원본 사진·서버 백업과 기존 DB를 확보할 수 없어 신규 DB로 시작한다. 과거 데이터는 이관하지 않으며 Phase 7에서 전환 직전 진행 중 신청 내역을 별도 보관한다. 공개 이미지 raw는 권리 `미확인(D6)` 상태로 커밋하지 않는다.

## 7. 인증·권한 [확정 원칙 + Claude 작성]

### 원칙 [확정]
- 공개 회원가입·로그인을 제공합니다. 회원은 가입·로그인 유지·아이디/비밀번호 찾기·정보 수정·탈퇴를 할 수 있으며, 신청은 비회원도 할 수 있습니다. 본인인증·그누보드 전용 항목(포인트·성인인증·접근그룹)은 제공하지 않습니다. (사용자 확인 2026-11-11, ASM-002)
- 관리자만 로그인합니다. 세션은 HttpOnly·Secure·SameSite 쿠키입니다.
- 권한 확인은 서버에서 매 요청마다 합니다. 화면에서 숨기는 것은 권한 처리가 아닙니다.
- 관리자 로그인 실패는 횟수를 제한합니다.

### 역할과 권한표 [Claude 작성 — D5 결정 후]
| 역할 | 볼 수 있는 것 | 바꿀 수 있는 것 |
|---|---|---|
| MEMBER | 본인 계정·본인 예약 | 본인 정보 수정·탈퇴 |
| ADMIN | 모든 관리자 기능·PII 감사기록 | 단일 역할의 콘텐츠·상태·계정·보존 설정 관리 |

## 8. URL·SEO 호환 [확정 원칙 + Claude 작성]

### 원칙 [확정]
- 공개 URL은 같은 경로를 유지하거나 308로 옮깁니다. 정말 없앨 페이지만 410을 씁니다.
- 매핑의 원본은 `docs/contracts/route-compatibility-map.json` 하나입니다.
- 레거시의 title, description, canonical, OG를 페이지마다 이식합니다.
- 전환 후 404 로그를 지켜보고 빠진 URL은 바로 매핑에 추가합니다.

### 매핑 요약 [Claude 작성 — Phase 2]
유지 10개 / 308 5개 / 410 2개 / 외부 유지 1개. `/uAdmin/**`와 `/adm/**`는 보안상 새 `/admin`을 노출하지 않는다. 상세는 `route-compatibility-map.json`.

## 10. 개인정보·보안 [확정]

- 신청자 다수가 학생(미성년자)과 학부모라고 보고 설계합니다.
- 수집 항목은 레거시 수준을 넘지 않습니다. 줄일 수 있으면 줄이는 안을 제안합니다.
- 레거시의 개인정보 수집·이용 동의 문구를 그대로 보존하고, 동의 여부와 시각을 저장합니다.
- 로그·에러 메시지·클라이언트 번들에 개인정보를 남기지 않습니다.
- 관리자 목록 화면은 이름·연락처를 기본으로 일부 가립니다.
- 비밀값은 환경 변수로만 관리합니다.
- 보안 헤더(CSP 등)와 요청 횟수 제한(rate limit)을 적용합니다.
