# 레거시 기록 처리 절차 (이관 불가 기록)

> 대상: 원장님·실무 직원. Phase 7에서 작성. 근거 등급은 `CLAUDE.md` 2장을 따릅니다.
> 관련: `docs/migration-checklist.md` · `docs/rollback-plan.md` · `docs/decisions/ADR-003`

---

## 1. 왜 "이관 불가"인가 (D1, `OBSERVED`)

새 사이트로 **옛 사이트의 신청 기록을 옮기지 않습니다.** 옮길 방법이 없습니다.

- 옛 사이트는 PHP + MySQL 로 돌아가고, 그 **데이터베이스와 서버 파일에 접근할 수 없습니다.**
  (호스팅 계정·DB 비밀번호를 확보하지 못했습니다 — D1, ADR-003)
- 관리자 화면에서 눈으로 볼 수 있는 것과 CSV 로 내려받을 수 있는 것이 전부입니다.
- 그래서 새 사이트는 **빈 데이터베이스로 시작**합니다. 전환 시점 이후의 신청만 새 사이트에 쌓입니다.

이 문서는 "그러면 전환 직전까지 들어온 신청은 어떻게 하느냐"에 대한 절차입니다.

---

## 2. 전환 직전, 진행 중인 신청을 직원이 따로 보관하는 방법

전환 **하루 전**에 합니다. 담당: 실무 직원 1명(기록 담당)과 확인자 1명.

### 2-1. 무엇을 보관하는가

옛 관리자 화면에서 **아직 처리가 끝나지 않은 것만** 보관합니다. 네 가지입니다.

| 옛 관리자 메뉴 | 보관 대상 | 새 사이트에서 이어지는 자리 |
|---|---|---|
| 강좌 예약(신청) 내역 | 수업이 아직 시작하지 않은 신청 | `/admin/course-applications` (AD-008) |
| 문자신청내역 | 다음 설명회 알림을 받기로 한 분 | `/admin/sms-subscriptions` (AD-010) |
| 입학진단관리(진단 상담) | 상담 날짜가 아직 오지 않은 신청 | `/admin/consultations` (AD-009) |
| 강사지원관리 | 검토가 끝나지 않은 지원 | `/admin/instructor-applications` (AD-011) |

**이미 끝난 기록(지난 설명회, 종료된 수업, 채용이 끝난 지원)은 보관하지 않습니다.**
남겨 둘 이유가 없는 개인정보는 옮기지 않는 것이 맞습니다. (`CLAUDE.md` 4장)

### 2-2. 어떻게 보관하는가

1. 옛 관리자 화면에서 목록을 **CSV 로 내려받습니다.** 내려받기가 없으면 화면을 인쇄물로 남깁니다.
2. 파일은 **학원 안의 컴퓨터 한 대**에만 둡니다. 암호를 건 폴더에 넣습니다.
   개인 메일·메신저·개인 USB·개인 클라우드로 보내지 않습니다.
3. 파일 이름에 `2026-00-00_강좌신청_전환직전` 처럼 **날짜와 종류**를 적습니다.
4. 보관 사실을 종이 한 장에 적어 둡니다: 날짜 / 종류 / 건수 / 보관한 사람 / 확인한 사람.
5. **새 사이트에 손으로 다시 입력하지 않습니다.** 옛 신청은 옛 기록으로 처리를 끝내고,
   새 사이트에는 전환 이후의 신청만 받습니다. 양쪽에 같은 분이 두 번 들어가면
   연락이 두 번 가거나 한 번도 가지 않습니다.

### 2-3. 보관한 파일을 언제 지우는가

- 그 신청의 **처리가 끝나는 날**(수업 시작, 상담 완료, 채용 종료)까지만 둡니다.
- 처리가 끝나면 파일을 지우고, 2-2의 종이에 "지운 날짜"를 적습니다.
- 늦어도 **전환 후 6개월**에는 남은 파일을 모두 지웁니다. 지우는 날짜를 미리 달력에 적어 둡니다.
- 새 사이트의 자동 파기(AD-013)는 **새 사이트에 들어온 기록만** 지웁니다.
  이 보관 파일은 사람이 직접 지워야 합니다.

> `UNKNOWN` — 위 "6개월"은 기본안입니다. 학원에서 정한 개인정보 보유 기간이 따로 있으면
> 그 기간을 씁니다. 원장님 확인이 필요합니다 (`Q-ADM-21`).

## 3. 전환 후 옛 관리자 화면을 언제까지 열어 두는가

**사람이 결정합니다.** Claude 가 정하지 않습니다. 결정에 필요한 사실만 적습니다.

### 3-1. 선택지

| 안 | 내용 | 좋은 점 | 걱정되는 점 |
|---|---|---|---|
| A (추천) | 전환 후 **1개월** 동안 옛 관리자만 열어 두고, 공개 화면은 전환 즉시 새 사이트로 넘긴다 | 전환 직전 신청을 옛 화면에서 그대로 확인할 수 있다 | 옛 서버 비용이 1개월 더 든다 |
| B | 전환과 동시에 옛 사이트를 완전히 닫는다 | 개인정보가 한 곳에만 남는다 | 2장에서 내려받은 CSV 가 유일한 기록이 된다 |
| C | 3개월 이상 열어 둔다 | 여유가 있다 | 관리하지 않는 PHP 관리자 화면이 오래 남는다. 보안상 권하지 않는다 |

### 3-2. 어느 안이든 반드시 하는 것

- 옛 관리자 화면 주소를 **직원 외에게 알리지 않습니다.** 새 사이트 어디에도 링크하지 않습니다.
- 옛 사이트의 **신청 폼은 전환 시점에 멈춥니다**(3장 B안이 아니어도). 새 신청이 옛 DB 로 들어가면
  아무도 보지 않는 곳에 개인정보가 쌓입니다. 멈추는 방법은 `docs/migration-checklist.md` 1-2 에 있습니다.
- 닫는 날 **옛 호스팅의 데이터베이스 백업을 한 번 받아 두고**, 받은 백업도 3-1의 기간이 지나면 지웁니다.
  (받을 수 있으면 받습니다. D1 기준으로는 받을 수 없는 상태입니다.)
- 닫은 뒤 `/uAdmin/`·`/adm/` 주소는 새 사이트가 **410 Gone** 으로 답합니다. 이미 구현되어 있습니다 (RT-004).

### 3-3. 결정 기록 자리

| 항목 | 결정 | 결정한 사람 | 날짜 |
|---|---|---|---|
| 옛 관리자 유지 기간 | (A / B / C 중 선택) | | |
| 옛 사이트 완전 종료일 | | | |
| 보관 CSV 파기일 | | | |

## 4. 전환 중에 새 사이트로 들어온 신청

전환 작업 중(DNS 가 퍼지는 몇 시간)에는 **두 사이트가 동시에 보일 수 있습니다.**
어느 쪽으로 신청이 들어와도 잃지 않도록 하는 방법은 `docs/rollback-plan.md` 4장에 있습니다.
