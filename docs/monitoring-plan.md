Vercel 에 배포하면 아래는 **설정 없이** 들어옵니다. 전환 직후 1주일은 이것만으로 충분합니다.

| 런타임 오류 | Vercel → 프로젝트 → **Runtime Errors** | 보관 기간이 짧다(Hobby 1일 / Pro 7일). **알림이 오지 않는다** — 사람이 열어 봐야 한다 |
| 요청 기록 | Vercel → **Logs** | 같다. 개인정보는 기록하지 않도록 이미 해 두었다 (`CLAUDE.md` 4장) |

**가장 큰 빈틈: 알림이 없습니다.** 사이트가 밤에 죽어도 아침에 누가 열어 볼 때까지 모릅니다.

## 1. 오류 추적 (무엇이 깨졌는지 알려 주는 것)

| 안 | 서비스 | 무료 한도 | 유료 | 좋은 점 | 걱정되는 점 |
|---|---|---|---|---|---|
| **1-A (추천)** | 아무것도 안 붙이고 Vercel Runtime Errors 를 **주 1회 사람이 확인** | 0원 | — | 개인정보가 외부로 나가지 않는다. 설정이 없다 | 알림이 없다. 보관이 짧다 |
| 1-B | **Sentry** | 월 5,000건 오류 · 1명 | 약 \$26/월부터 | 오류가 나면 **메일·슬랙으로 바로 알려 준다**. 어느 줄에서 깨졌는지 보인다 | 오류 메시지에 신청자 정보가 섞여 나갈 수 있다 → `sendDefaultPii: false` 와 가림 설정 필수 |
| 1-C | **Vercel Observability Plus** | — | \$10/월 (프로젝트 아님, 계정) | Vercel 안에서 끝난다. 외부 업체가 늘지 않는다 | 알림 조건이 Sentry 보다 단순하다 |

> **개인정보 주의** — 오류 추적을 붙이면 오류가 난 요청의 입력값이 함께 올라갈 수 있습니다.
> 우리는 신청 폼으로 이름·연락처를 받습니다. 붙이기로 정하면 **값을 보내지 않는 설정**을
> 먼저 넣고, 테스트 신청으로 실제로 값이 안 나가는지 확인한 뒤에 켭니다.

**추천 경로**: 전환 후 1개월은 1-A. 오류를 사람이 못 따라갈 정도로 많아지면 1-B 를 검토.

## 2. 가동 감시 (사이트가 살아 있는지 보는 것)

1~5분마다 사이트를 열어 보고, 안 열리면 알려 주는 것입니다. **전환 직후에 가장 쓸모 있습니다.**

| 안 | 서비스 | 무료 한도 | 유료 | 좋은 점 | 걱정되는 점 |
|---|---|---|---|---|---|
| **2-A (추천)** | **UptimeRobot** | 5분 간격 · 50개 주소 · 메일 알림 | \$7/월 (1분 간격, 문자) | 무료로 충분하다. 5분 안에 메일이 온다 | 무료는 문자 알림이 없다 |
| 2-B | **Better Stack (Uptime)** | 3분 간격 · 10개 주소 | \$29/월 | 화면이 보기 좋다. 상태 페이지를 만들 수 있다 | 무료 한도가 더 좁다 |
| 2-C | **Vercel 안에서** | — | — | 외부 업체가 늘지 않는다 | **없다.** Vercel 에는 가동 감시가 없다 |

### 감시할 주소 (어느 안을 고르든 같다)

| 주소 | 기대 | 왜 |
|---|---|---|
| `https://munsayu.com/` | 200 | 홈이 열리는지 |
| `https://munsayu.com/sub/Presentation` | 200 | 설명회 — 신청이 몰리는 화면 |
| `https://munsayu.com/notice` | 200 | 데이터베이스까지 살아 있는지 (목록을 DB 에서 읽는다) |
| `https://munsayu.com/admin/login` | 200 | 관리자 화면이 사는지 |

- **신청 폼에 실제 신청을 보내는 감시는 넣지 않습니다.** 가짜 신청이 쌓입니다 (`CLAUDE.md` 3장 2번).
- 알림 받을 주소: 원장님 메일 + 직원 메일 **두 곳**. 한 곳만 두면 그 사람이 휴가일 때 아무도 모릅니다.

**추천 경로**: 전환 **전날** 2-A 를 무료로 붙입니다. 전환 당일 가장 먼저 알려 주는 장치가 됩니다.

> 전환 전날 등록해 두면 전환 전까지는 **옛 사이트**를 보고, 전환 후에는 같은 주소가
> 새 사이트를 가리키므로 **고칠 것이 없습니다.** 덤으로 옛 사이트의 평소 응답 시간이
> 기준값으로 남습니다.
>
> 전환 전에 **스테이징 주소**(`...vercel.app`)를 감시하려면 한 가지 주의가 필요합니다.
> 지금 프로젝트는 **Vercel 로그인 보호가 켜져 있어** 바깥에서 열면 로그인 화면(401)이
> 나옵니다. 감시 도구는 이것을 「죽었다」로 봅니다. 스테이징은 감시 대상에서 빼고,
> 전환 후 `munsayu.com` 만 감시하세요.

## 3. 신청 건수 이상 감지 (폼이 조용히 깨진 것을 잡는 것)

가장 무서운 고장은 "사이트는 열리는데 신청만 저장되지 않는" 경우입니다.
화면은 멀쩡하니 가동 감시도 오류 추적도 아무 말을 하지 않습니다. **몇 주 뒤에 "왜 연락이 없냐"는
전화로 알게 됩니다.** 신청 건수를 보는 것이 이걸 잡는 유일한 방법입니다.

| 안 | 방법 | 비용 | 좋은 점 | 걱정되는 점 |
|---|---|---|---|---|
| **3-A (추천, 1단계)** | 직원이 **매일 아침** 관리자 화면에서 어제 건수를 본다. 0건이 **2일 연속**이면 개발에 알린다 | 0원 | 지금 바로 할 수 있다. 추가 코드가 없다 | 사람이 잊는다. 주말에 비어 있다 |
| 3-B (2단계) | 하루 한 번 건수를 세어 **0건이면 메일**을 보내는 예약 실행을 새로 만든다 | 0원 (Vercel Cron 무료 한도 안) | 자동이다. 외부 업체가 없다 | 만드는 일이 생긴다(작업 반나절). 메일 발송이 동작해야 한다 (D4) |
| 3-C | 외부 분석 도구(GA4)에서 완료 화면 도달 수를 보고 알림을 건다 | 0원 (GA4) | 방문 수와 함께 본다 | 설정이 번거롭다. GA4 알림은 느리다(하루 단위) |

### 기준선 (어느 안이든 필요)

전환 후 **2주**간 건수를 적어 평소 값을 만듭니다. 그게 없으면 "적다"를 판단할 수 없습니다.

| 종류 | 평소 하루 건수 | 적다고 볼 기준 |
|---|---|---|
| 강좌 신청 | (2주 기록 후 채움) | |
| 설명회 예약 | | |
| 설명회 알림 신청 | | |
| 진단 상담 | | |
| 강사 지원 | | 원래 드물다. 0건이 정상 |

> 설명회·수강 신청은 **시즌에 따라 10배 차이**가 납니다. "지난주 같은 요일과 비교" 가
> "어제와 비교" 보다 맞습니다.

**추천 경로**: 전환 즉시 3-A. 기준선이 모이는 2주 뒤에 3-B 를 만들지 결정.
