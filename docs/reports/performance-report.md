# 성능 보고서 — Phase 6

> 로컬 프로덕션 빌드(`next build` → `next start`) 기준. 운영 사이트에는 접속하지 않았다.
> 측정 스크립트 `scripts/measure-web-vitals.ts` · 원자료 `docs/evidence/perf/vitals-{before,after}.json`

---

## 1. 어떻게 쟀나

Lighthouse 를 devDependency 로 넣지 않고 CDP 로 직접 쟀다. 조건은 Lighthouse 모바일
기본값과 같게 맞췄다.

| 항목 | 값 |
|---|---|
| 화면 | 375x667, DPR 2, 모바일 |
| CPU | 4배 느리게 |
| 네트워크 | 느린 4G — 1.6Mbps 받기 / 750kbps 보내기 / RTT 150ms |
| 횟수 | 화면마다 3번 측정 후 가운데 값 |

- **LCP**: `largest-contentful-paint` 의 마지막 값
- **CLS**: 사용자 입력 없이 일어난 `layout-shift` 를 세션 창으로 묶은 최댓값
- **INP 대신 TBT**: INP 는 실제 사람의 조작이 있어야 나온다. 합성 측정에서는
  Lighthouse 와 같이 **TBT(긴 작업 50ms 초과분의 합)** 를 대용값으로 본다.
  이 점은 Gate 판정에 그대로 적어 두었다.

## 3. 무엇이 문제였나

측정해 보니 **홈이 가장 빨랐다.** 가장 무거운 화면이 가장 빠른 것은 이상한 신호라
리소스를 따라갔더니 원인이 하나였다.

```
LCP: /images/hero/sub-hero.avif  (CSS 배경, 272,960B)  → 2918ms 에 도착
```

모든 `/sub/*` 과 공지 화면이 쓰는 상단 배너였다.

- 원본이 **1920x1280 · 267KB** 인데 CSS `background-image` 는 화면 크기에 맞춰
  줄여 주지 않는다. 375px 휴대폰도 1920px 원본을 그대로 받았다.
- CSS 배경이라 `next/image` 의 최적화·`priority`·미리 불러오기가 하나도 걸리지 않았다.
- 게다가 이 사진 위에는 **80~90% 불투명한 덮개**가 깔린다. 사진은 분위기만 내는데
  화면에서 가장 무거운 자원이었다.

## 4. 무엇을 고쳤나

| # | 고친 것 | 효과 |
|---|---|---|
| P1 | 상단 배너를 CSS 배경 → `next/image` (`fill` + `priority` + `sizes="100vw"`) | 화면 폭에 맞는 파일을 내려주고 미리 불러온다 |
| P2 | 홈 배너 3장도 `next/image` 로. **첫 장만 `priority`**, 2·3장은 느긋하게 | 첫 화면에 필요한 것만 먼저 받는다 |
| P3 | `images.formats` 에 AVIF 추가 (기본은 WebP 하나뿐이었다) | 같은 배너 WebP 32KB → **AVIF 10KB** |
| P4 | `images.qualities` 에 55 등록 | 등록하지 않으면 `quality` 를 넘겨도 기본 75 로 되돌아간다 |

**배너 전송량 267KB → 10KB (375px 기준, 96% 감소).**

사진 위 덮개가 두꺼워 품질을 낮춰도 눈에 띄지 않는다. 시각 회귀 104건이 기준 이미지를
그대로 통과해 **보이는 모습이 달라지지 않았음**을 확인했다.

## 5. 따로 손댈 것이 없었던 항목

| 항목 | 확인 결과 |
|---|---|
| Bootstrap JS · AOS · jQuery | **애초에 없다.** 레거시 전용 라이브러리라 이관하지 않았다. 런타임 의존성은 12개뿐이다 |
| 폰트 로딩 | 웹폰트 파일이 없다. 시스템 글꼴 묶음만 쓴다(ASM-041). 받을 폰트가 없으니 지연도 없다 |
| 불필요한 Client Component | 38개 중 대부분이 관리자 화면이다. 공개 화면 쪽은 6개뿐이고 TBT 가 5~36ms 로 기준(200ms)의 20% 미만이라 줄일 이유가 없다 |
| CLS | 모든 화면 0.000. 사진에 크기가 지정돼 있어 밀림이 없다 |
| 관리자 목록 N+1 | 없다. 목록은 모두 `Promise.all([count, findMany])` 이고 관련 자료는 `include`·`in` 으로 한 번에 받는다. 반복문 안의 `await` 2곳은 DB 가 아니라 파일 삭제였다 |
| 색인 | `@@index`·`@unique` 59개. 목록의 정렬 기준(`createdAt`)과 주요 필터가 덮인다 |

## 6. 찾아서 고친 것 — CSV 내보내기에 상한이 없었다

성능과 개인정보가 함께 걸린 문제라 여기에 적는다.

내보내기 4개(`신청·예약`·`상담`·`알림 신청`·`강사 지원`)가 **모두 `take` 없이**
조건에 맞는 모든 줄을 메모리에 올려 한 덩어리 문자열로 만들고 있었다. 필터 없이 한 번
누르면 표 전체가 올라간다. 함수 메모리 한계에 걸릴 수 있고, 개인정보가 담긴 파일이
한 번에 통째로 빠져나간다.

**조용히 잘라내지 않는다.** 「현재 필터 결과 전체」라는 약속(ASM-006)이 거짓이 되기
때문이다. 2만 줄을 넘으면 거절하면서 범위를 좁히라고 알려 준다. // ASM-097
한 번에 상한+1 만큼만 읽어 메모리에 올라오는 양을 실제로 묶는다.

## 7. 신청 API 부하 테스트

`scripts/load-test-applications.ts` — **로컬 전용**이다. 로컬 주소가 아니면 멈춘다.
보내는 자료는 전부 가짜다(`부하테스트N`, `010-0000-xxxx`).

| 설정 | 결과 |
|---|---|
| 동시 10 · 200건 · IP 하나 | 201 **60건** / 429 **140건** / 5xx **0건** — 요청 횟수 제한(60회/60초, ASM-022)이 정확히 걸렸다 |
| 동시 20 · 500건 · IP 분산 | 201 **500건** / 5xx **0건** · 1,066건/초 · p50 18ms · p95 26ms · p99 34ms |

오류율 **0%**. 두 번째 실행은 횟수 제한을 피해 처리 능력 자체를 본 것이고, 첫 번째는
제한이 제 일을 하는지 본 것이다.

> Gate 기준은 「**스테이징** 부하 테스트」지만 스테이징은 Phase 7 에서 만든다.
> 사용자 지시도 「로컬 실행만」이었다. 스테이징이 서면 같은 스크립트를
> `LOAD_TEST_BASE` 로 가리켜 다시 돌린다.
