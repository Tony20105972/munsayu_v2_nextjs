# ADR-008 — 관리자 이미지 업로드와 이미지 보관함 (AD-015)

- 상태: 확정
- 날짜: 2026-11-14
- 결정한 사람: 사용자 (2026-11-14 지시)
- 관련 근거: EV-0012 (레거시 이미지 지도), `docs/legacy/legacy-assets.json`, D6 (이미지 권리), ASM-008 (저장소 어댑터)
- 관련 ADR: ADR-003 (배포·DB), ADR-006 (공지 편집기·정리기), ADR-007 (Phase 5 관리자 범위)

## 배경

Phase 3·4까지 공개 화면의 사진은 모두 **코드에 박혀** 있었다.
`src/lib/images.ts` 의 등록부와 `public/images/` 의 커밋된 파일이 짝이었고,
사진을 바꾸려면 개발자가 저장소를 고쳐 배포해야 했다. 강사 사진은 커밋된 파일 키를
관리자가 **고르는 것만** 가능했고(새 파일을 올릴 수는 없었다), 메인 배너와 시설안내
사진은 아예 코드 상수였다.

AD-014 공지 본문 이미지만 업로드가 있었지만 그 경로는

- 형식 검사만 하고 크기를 줄이거나 EXIF 를 지우지 않았고,
- 대체 텍스트를 빈 값으로 넣었고,
- 로컬에서 저장한 파일을 **내보낼 경로가 없어서** 올린 사진이 화면에 뜨지 않았다
  (`urlFor()` 가 `/uploads/...` 를 돌려주는데 그 경로를 받는 핸들러가 없었다).

사용자 지시(2026-11-14): 관리자가 새 사진을 직접 올려 사이트 사진을 추가·교체할 수 있게 한다.

## 결정

### 1. 기능 ID 는 AD-015 로 새로 붙인다

이미지 관리는 레거시 관리자 메뉴에 없던 신규 기능이다. 관찰 근거로 정당화할 수 없으므로
기존 AD-006/AD-014 안에 숨기지 않고 별도 ID 를 붙여 범위 변경을 드러낸다.

### 2. 올리기는 「서버 티켓 → 브라우저가 저장소로 직접 → 서버 재검사」 세 걸음

**이유: Vercel 함수의 요청 본문 상한이 4.5MB 다.**
공식 문서에서 확인했다 — "The maximum payload size for the request body or the response
body of a Vercel Function is **4.5 MB**. … 413: `FUNCTION_PAYLOAD_TOO_LARGE`"
(<https://vercel.com/docs/functions/limitations>, 확인 2026-11-14, 문서 갱신일 2026-08-24).

20MB 사진을 Server Action 으로 보내면 **운영에서 반드시 실패한다.** 그래서 파일 바이트가
함수를 지나가지 않게 한다.

| 걸음 | 하는 일                                                                  | 어디서                    |
| ---- | ------------------------------------------------------------------------ | ------------------------- |
| 1    | 관리자 권한 확인, 용량 상한 결정, 임시 저장 자리와 **서명된 티켓** 발급  | `createMediaUploadTicket` |
| 2    | 파일 바이트를 저장소로 직접 전송                                         | 브라우저 → 저장소         |
| 3    | 저장된 것을 서버가 읽어 형식·용량 재검사, 변환, 보관함 등록, 임시본 삭제 | `finalizeMediaUpload`     |

- 검사는 **항상 서버에서** 한다. 브라우저가 알려 준 파일 형식·크기는 믿지 않는다.
- 2번을 건너뛰고 1·3번만 불러도 임시 저장본이 없어 실패한다.
- 임시 저장 영역(`staging`)은 공개 주소를 만들지 않는다. 검사 전 원본은 성공이든 실패든 지운다.

### 3. 로컬과 운영의 어댑터

`StorageAdapter` 에 `createUploadTicket()` 을 추가해 두 구현이 같은 모양을 쓴다.

- **로컬(지금):** 티켓 주소는 우리 경로 `PUT /api/admin/media/direct-upload` 다.
  그 경로는 **관리자 세션과 티켓 서명을 모두** 확인한다. 티켓만으로는 통과하지 않는다.
  서명은 `AUTH_SECRET` 에서 갈라 만든 키로 HMAC-SHA256 하고, 영역·키·상한·만료를 담는다.
  본문은 스트림으로 읽으며 상한을 넘는 즉시 끊는다(메모리 보호).
- **운영(Phase 7):** Vercel Blob 클라이언트 업로드로 바꾼다.
  `@vercel/blob/client` 의 `upload()` + 서버의 `handleUpload()` 가 같은 역할을 한다
  (`onBeforeGenerateToken` 에서 관리자 권한 확인 → 클라이언트 토큰 발급).
  **이번 작업에서는 구현하지 않았다.** 의존성을 미리 넣고 검증 없이 두는 것보다
  Phase 7 에서 실제 Blob 저장소에 붙여 확인하는 쪽이 안전하다.
  `next.config.ts` 의 `images.remotePatterns` 에 Blob 호스트를 미리 열어 두었다.

### 4. 저장 전 처리 — 원본은 보관하지 않는다

| 항목        | 결정                                                                     |
| ----------- | ------------------------------------------------------------------------ |
| 허용 형식   | JPG, PNG, WebP, GIF. **파일 내용(시그니처)** 으로 판별한다               |
| SVG         | 받지 않는다. 안에 스크립트를 넣을 수 있다                                |
| HEIC/HEIF   | 서버에서 JPG 변환을 **시도**하고, 못 하면 쉬운 안내를 돌려준다 (ASM-091) |
| 용량        | 기본 20MB. 관리자 설정 `media.upload.maxBytes` 로 바꾼다                 |
| 크기        | 긴 변 2000px 이하로 줄인다. 원본이 더 작으면 그대로 둔다                 |
| EXIF        | 지운다. 촬영 위치(GPS)가 사진에 남지 않게 한다                           |
| 방향        | EXIF Orientation 을 픽셀에 반영한 뒤 지운다                              |
| 대체 텍스트 | **필수.** 화면·Action·서비스 세 곳에서 모두 확인한다                     |

`sharp` 를 직접 의존성에 넣었다. 이미 `next` 의 전이 의존성으로 설치돼 있었고(번들된
libvips 8.18.7), 이미지 처리 라이브러리를 두 개 넣지 않기 위해 같은 것을 쓴다.
`sharp` 는 `.withMetadata()` 를 부르지 않으면 메타데이터를 빼고 다시 쓰므로 EXIF 제거는
재인코딩 자체로 이뤄진다. 지웠는지는 테스트로 확인한다.

### 5. 보관함(`MediaAsset`)이 단일 등록부

공개 화면이 쓰는 이미지는 모두 이 표를 거친다.

- `UPLOAD`: 관리자가 올린 파일. StorageAdapter 공개 영역에 있다.
- `LEGACY`: 레거시에서 받아 `public/images/` 에 커밋한 파일. 저장소에는 없고 행만 있다.
  `docs/legacy/legacy-assets.json` 의 권리 표시를 함께 보여 주고, "Unsplash" 표시가
  붙은 사진은 `replaceRecommended = true` 로 「교체 권장」을 띄운다. (D6)

**쓰이는 자리는 참조하는 표를 직접 보고 찾는다.** 따로 사용 기록 표를 두지 않았다.
사용 기록을 복제하면 실제 참조와 어긋날 수 있고, 어긋난 사용 기록은 "쓰는 중인데 지워지는"
사고로 이어진다. 지금 보는 곳은 `Instructor.photoMediaId`, `HomeBanner.mediaId`,
`FacilityPhoto.mediaId`, 그리고 `Notice.body` 안의 주소 네 군데다.
화면에서 쓰는 중인 사진은 삭제를 막고 어디에 쓰는지 알려 준다.

### 6. 화면 연결과 복원력

| 화면          | 연결 방식                                       | 값이 없을 때                          |
| ------------- | ----------------------------------------------- | ------------------------------------- |
| 강사 사진     | `Instructor.photoMediaId`                       | 레거시 이름 매핑 → 학원 로고 자리표시 |
| 메인 배너     | `HomeBanner` 행 (사진·제목·설명·버튼·순서·노출) | 코드 기본값 3장 (Phase 3 문구 그대로) |
| 시설안내 사진 | `FacilityPhoto` 행 (지점·순서·설명·노출)        | 커밋된 지점별 4장                     |
| 공지 본문     | AD-014 편집기가 같은 업로드를 쓴다              | —                                     |

**DB 를 읽지 못하거나 행이 없어도 페이지 전체가 멈추지 않는다.** 배너·시설 사진 조회와
`getSiteSettings()` 는 실패를 잡아 코드 기본값을 돌려준다. 기다리는 동안 보여 주는 값도
기본값이라 화면이 비거나 흔들리지 않는다.

`Instructor.photoStorageKey` 는 지웠다. 커밋된 파일 키와 보관함 사진 id 를 동시에 두면
"어느 쪽이 이기는지" 가 코드마다 달라진다. 레거시 데이터 이관이 없으므로(D1, ADR-003)
칸을 바꾸고 시드가 이름으로 사진을 다시 붙인다.

### 6-1. 삭제는 지우고, 기존 사이트 사진은 숨긴다

사용자 지시(2026-11-14): 보관함에서 한 장·여러 장을 지울 수 있게 한다.

| 사진                        | 「지우기」                                      | 「숨기기」                   |
| --------------------------- | ----------------------------------------------- | ---------------------------- |
| 올린 사진 (`UPLOAD`)        | 보관함 기록 + 저장소 파일을 **한 트랜잭션**으로 | 된다 (지우지 않고 치워 두기) |
| 기존 사이트 사진 (`LEGACY`) | **막는다** — 파일이 `public/` 에 커밋돼 있다    | 된다 (이 길만 있다)          |
| 쓰는 중인 사진              | 막는다 (쓰는 곳을 돌려준다)                     | 막는다                       |

- **파일 삭제가 실패하면 기록도 지우지 않는다.** 기록 삭제와 파일 삭제를 한 트랜잭션에
  묶어 파일 쪽이 실패하면 되돌린다. 목록에 남아 다시 지울 수 있는 것이, 보이지 않는
  파일이 저장소에 남는 것보다 낫다.
- **기존 사이트 사진은 실행 중에 파일을 지울 수 없다.** 배포본의 `public/` 은 읽기 전용이고,
  파일을 지우려면 저장소를 고쳐 다시 배포해야 한다. 그래서 `MediaAsset.hiddenAt` 을 두고
  목록·사진 고르기에서 빼는 「숨기기」로 처리한다. 숨긴 사진은 화면에 **새로 붙지 않는다**
  (`assertMediaExists` 가 막는다). 다시 보이게 하면 그대로 돌아온다.
- **쓰는 중인 사진은 숨기기도 막는다.** 공개 화면은 계속 그 사진을 쓰는데 보관함에서만
  사라지면 되돌릴 자리를 찾을 수 없다.
- **선택 삭제는 한 장이 막혀도 나머지를 지운다.** 지운 것과 막힌 것을 함께 돌려주고
  (`MediaDeleteResult`) 화면이 「2장 지웠고 1장은 쓰는 중이라 남겼습니다」처럼 알려 준다.
  한 번에 50장까지만 받는다(`MEDIA_BULK_DELETE_MAX`) — 실수로 대량 삭제하는 것을 막는다.
- 화면(Server Action)과 API(`DELETE /api/admin/media`, `POST /api/admin/media/hide`)가
  같은 서비스 함수를 쓴다. 권한은 두 길에서 **각각 다시** 확인한다.

### 7. 감사 기록

`AuditAction` 에 `MEDIA_UPLOAD` · `MEDIA_UPDATE` · `MEDIA_DELETE` ·
`MEDIA_HIDE` · `MEDIA_UNHIDE` 를 더했다.
올리기·대체 텍스트 수정·삭제·숨기기·다시 보이기, 그리고 **화면에 사진을 붙이거나
바꾸거나 뺀 것**을 남긴다.
`filterSummary` 에는 형식·바이트·사진 id 만 넣고 **파일 이름은 넣지 않는다.** (AD-013)

### 8. 레거시 등록부는 생성해서 커밋한다

`scripts/build-legacy-media-registry.ts` 가 `public/images/` 를 읽어 크기·형식을 재고
권리 표시를 짝지어 `src/lib/legacy-media-registry.ts` 로 쓴다(`npm run build:media-registry`).

보관함 등록은 운영 함수에서도 돌아야 하는데 함수 번들에 `public/` 이 들어온다는 보장이
없다. 파일을 읽는 일을 작성 시점에 끝내 두면 등록은 DB 작업만 남는다.

## 함께 고친 것

- **`/uploads/[...key]` 경로를 새로 만들었다.** 로컬 어댑터가 저장소 바깥
  (`.storage/public/`)에 파일을 두므로 정적으로 제공되지 않는다. 이 경로가 없어서
  AD-014 가 올린 공지 본문 이미지는 로컬에서 **뜨지 않았다**(기존 결함). 이미지 확장자만
  내보내고 `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`,
  `Content-Disposition: inline` 을 붙인다.
- 공지 본문 이미지 업로드(`uploadNoticeImage`)를 지우고 공통 업로드로 바꿨다.
  이제 공지 사진에도 크기 줄이기·EXIF 제거·대체 텍스트가 똑같이 적용된다.
- 홈 배너 슬라이드 CSS 를 장수에 맞게 변수로 바꿨다. 움직임을 줄이도록 설정한 환경에서
  **모든 슬라이드가 한꺼번에 겹쳐 보이던 문제**도 함께 고쳤다(슬라이드마다 제목이 따로
  생겼으므로 반드시 끊어야 한다).
- 로컬 어댑터의 경로 계산에 `turbopackIgnore` 를 달았다. 빌드가 "저장소 전체를 함수
  번들에 넣는다"고 경고했고, 그대로 두면 `public/` 까지 함수에 들어가 배포가 커진다.

## 되돌리는 방법

1. 관리자 메뉴에서 「이미지 관리」를 지우고 `/admin/media/**` 를 지운다.
2. 강사·배너·시설 화면을 코드 기본값만 쓰도록 되돌린다
   (`DEFAULT_HOME_BANNERS`, `DEFAULT_FACILITY_PHOTOS`, `resolveInstructorPhoto` 가 이미 그 값을 갖고 있다).
3. `MediaAsset`(`hiddenAt`·`hiddenByUserId` 포함)·`HomeBanner`·`FacilityPhoto` 표와
   `Instructor.photoMediaId` 를 지운다.
4. 올린 파일은 `StorageAdapter` 공개 영역에 남으므로 따로 지운다.

공개 화면은 보관함이 비어도 Phase 3 모양으로 그려지므로 1·2번만 해도 사이트는 정상이다.
